# LogiFlow Frontend / Backend Alignment Report

**Source of truth:** `LOGIFLOW_MANUFACTURER_DISTRIBUTOR_API_INTEGRATION_GUIDE.md` supplied with this task. The older `docs/LOGIFLOW_FINAL_BACKEND_API_SPECIFICATION.md` contains proposed/unverified contracts and was not used to override the supplied guide.

## Scope reviewed

Traced the Manufacturer and Distributor procurement path across routes, pages, services, API endpoint registry, models and status views: product discovery/publication, distribution authorization, PO submission/review, payment initiation/status, shipment creation/status, Distributor receipt, inventory restock and offer publication. Core files include `src/app/core/api/api-endpoints.ts`, `src/app/features/distributor/catalog`, `src/app/features/distributor/procurement`, `src/app/features/manufacturer/products`, `src/app/features/manufacturer/purchase-orders`, `src/app/features/manufacturer/shipments`, `src/app/features/distributor/warehouses`, and shared payment models/services.

## Findings and corrections

1. **Manufacturer shipment paths and payload were incompatible.** The UI used `/api/v1/shipments` and submitted UI-only destination text, quantity, driver and vehicle fields. The endpoint registry now uses `/api/v1/manufacturer/shipments` and its corresponding detail/status paths. The service sends only `purchaseOrderId`, `destinationWarehouseId`, and optional `carrier`, and maps backend shipment fields and statuses. The allocation form now asks for the destination Distributor warehouse UUID and keeps trip/driver/vehicle assignment separate, as the guide specifies.
2. **Shipment lifecycle was incomplete and conflated with trips.** Added `READY_FOR_DISPATCH`, `RECEIVED`, and `CANCELLED` handling. A ready shipment can transition to `IN_TRANSIT`, then to `DELIVERED`; receipt remains a distinct Distributor operation. Manufacturer cancellation is shown only to `MANUFACTURER_ADMIN`, and requires a reason. Shipment list/details no longer display invented shipment quantity, trip, or driver data as if those came from the shipment DTO.
   The Manufacturer warehouse operations page also used its local pick/pack ledger to create a shipment with unsupported fields. It now dispatches an already-created backend shipment through the documented status transition and links users to create the shipment first; local warehouse data is not presented as a persisted shipment manifest.
3. **Authorization API integration used the wrong collection and decision DTO.** Manufacturer incoming requests now load from `/api/v1/products/authorizations/incoming`; decision requests send `{status, note}` rather than `{decision}`. Distributor authorization records accept backend `manufacturerProductId`/`createdAt` field names. Distributor requests now include the guide's proposal fields (`requestNote`, `targetMarket`, `salesChannels`, `geographicalCoverage`, `distributionStrategy`). `REVOKED` is retained as a state and allows a new authorization request, consistent with the guide.
4. **Manufacturer PO permissions and rejection behavior were too broad/incomplete.** Only manufacturer administrators are offered/allowed to decide POs. Rejection now collects a reason. Existing internal “ACCEPTED” display naming is mapped from the backend's `APPROVED` enum; requests send backend `APPROVED`/`REJECTED` values.
5. **PO status values were incorrectly mixed with shipment progress in the Distributor workspace.** Distributor PO mapping now preserves the documented `SUBMITTED`, `APPROVED`, `REJECTED`, `CANCELLED`, and `FULFILLED` values. The payment initiation panel is available only for `APPROVED`; the submitted state waits for manufacturer review. The procurement dashboard counts `SUBMITTED` POs. This avoids treating shipment dispatch/delivery as PO state; the PO becomes `FULFILLED` on receipt.
6. **Payment verification did not use the documented PO status endpoint.** Both PO and customer order payment verification now query `/api/v1/payments/{orderId}/status`. `SETTLED` normalizes to the UI's confirmed-paid state; initiation remains pending and is not treated as success. Settlement list retrieval remains available on the PO details screen.
7. **Receipt and listing sequence matched the guide.** Existing Distributor warehouse operations submit one receipt line per PO item with accepted/damaged/missing totals, require `DELIVERED`, refetch warehouse inventory and PO data after success, and call the documented shipment-receive route. Existing offer logic creates a linked Distributor offer at zero stock and blocks activation until authorization and positive available stock are confirmed.

## Remaining gaps / backend clarifications

- **Destination warehouse discovery:** The guide requires `destinationWarehouseId` to belong to the Distributor, but documents no Manufacturer-accessible API to list eligible Distributor warehouses. The form therefore collects the warehouse UUID manually. Confirm a tenant-safe lookup route or a shared selection workflow; do not assume the PO's buyer organization ID is a warehouse ID.
- **Authorization commercial terms:** The guide allows a manufacturer to approve optional `agreedWholesalePrice` and `minimumOrderQuantity` together, but the current decision UI does not collect or display those terms. Approval without them is supported by the guide's fallback behavior. Confirm whether the workspace should expose terms entry; if yes, provide precision/range validation and display authoritative terms on the Distributor side.
- **Shipment receipt data in Manufacturer views:** The shipment response includes receipt lines and timestamps. The present adapter uses the core shipment identifiers/status/tracking fields; receipt-line discrepancy details are not shown on the Manufacturer shipment detail page. Confirm which receipt audit fields should be displayed to Manufacturer users.
- **Separate trip linkage:** The guide explicitly says PO shipments and trips are separate and shipment DTOs do not contain driver/vehicle assignment. Existing logistics pages still include legacy views derived from PO/shipment context and should be aligned to persisted `/api/v1/trips` data where they imply a live trip. No shipment-to-trip relationship field or endpoint is defined, so no link was invented here.
- **PO settlement response shape:** The guide names settlement statuses/history routes but gives only partial settlement DTO details. Manufacturer PO mapping reads an embedded latest `settlements` status when present, with the older `paymentStatus` fallback. Confirm the authoritative settlement DTO and ordering if the API does not embed settlements.
- **Cancellation authorization:** The guide says Manufacturer admin may cancel before completion but does not enumerate whether cancellation is permitted in every pre-completion status. The UI offers cancellation in `READY_FOR_DISPATCH` and `IN_TRANSIT`; the server remains authoritative for the allowed transition.
